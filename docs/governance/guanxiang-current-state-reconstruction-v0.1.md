## 1. 这次重建修正了什么

上一版重建的根本错误，是把 Git 分支、Gate、Stage 1E、测试批次等技术执行坐标放到了项目结构的上层。那种结构可以帮助工程审计，但无法回答产品负责人真正关心的三个问题：

1. 观象网站原本要做什么？
2. 现在做到第几页，为什么停下？
3. 下一步做什么才能继续接近完整产品？

本版改用产品语义作为唯一主结构：

```text
Project：观象
  Module：第一页
  Module：第二页
  ...
  Module：第十页
  Module：解卦系统（已正式升格为第十一模块）
```

Git、Gate、Stage 1E、测试和实验只挂在相关模块下面，作为实施证据、实验历史或风险记录，不再反过来定义产品。

### 2.2 Stage 1E 的真实归属

只读核对现有验收报告后可以确认：Stage 1、1B、1C、1D、1E 优化的是第四页“辨识”——即卜卦前怎样追问、识别决策瓶颈和形成最终卜题。

它不直接验证第八页解卦质量，也没有解决“同一个现实问题换一卦后，核心判断是否会真正改变”。后一个问题在阶段 0 中被明确留给后续 Stage 2，但尚未执行。

因此本版把 Stage 1E 归位为：

```text

```

Stage 1E 的技术 canary 3/3 通过仍是有效证据，但它只能证明三条辨识服务路径可执行，不能代表解卦系统或观象项目完成。产品负责人已经确认：Stage 1E 不暂停，先完成辨识系统，再恢复解卦系统。

## 3. 模块升格规则

模块不由文件夹或技术名字决定，而由产品责任决定。

当一个原本的任务同时出现以下特征时，应向产品负责人提出升格建议：

- 它决定产品核心用户价值；
- 它有独立目标和完成定义；
- 它包含多个阶段和大量任务；
- 它有独立风险、质量门和专业角色；
- 它会被多个页面或功能共同依赖；
- 不把它单独管理，就会让原页面模块无限膨胀。

解卦系统已经满足这些特征。产品负责人已于 2026-08-09 确认其正式成为第十一模块。

## 5. 已确认的解卦系统完成定义 v0.1

以下六项从 Gate 1、阶段 0 和产品负责人的实际不满中提炼，已由产品负责人确认按 v0.1 执行：

1. 真正回答用户最终确认的问题，而不是只总结资料。
2. 能说明为什么核心判断是由这个卦推出；换成另一个卦时，判断应产生可解释的变化。
3. 用户现实事实、程序排出的卦象事实和解释推断必须清楚分开。
4. 判断具体、有差异，不能不断坍缩成“先观察、做小步尝试、保持可逆”的通用谨慎话术。
5. 行动建议可执行，但不替用户决定、不读心、不承诺结果、不生成程序没有提供的具体日期。
6. 用户连续多次使用时，能感受到不同问题和不同卦象带来的真实差异，同时保持观象的产品声音。

任何后续 Gate、Stage 或实验都必须说明自己具体服务于哪一项标准，不能只因为测试通过就继续扩展。若要修改标准，需建立新版本并重新取得产品负责人确认。

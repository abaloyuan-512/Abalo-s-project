## 2. 反向论证结论

v0.1 的主方向可以保留：保护 V72，先建立匿名安全基座，再修移动端，随后按
小样本逐级开放。但原计划存在以下阻断项：

1. “Phase 2”名称与引擎既有阶段体系冲突。
2. 当前公开预算能力只计量，不存在自动硬上限。
3. Direct Reading V2 和 intake 尚未统一接入匿名频率、总预算、并发和幂等控制。
4. 匿名开放前缺少明确的高风险输入处理和固定安全测试集。
5. 停止开关没有操作人、生效范围、失败行为、恢复权限和演练证据。
6. Gate 1 要求手机完整通过、Gate 2 才修手机，存在依赖环。
7. 3 人、10 人和最多 30 人只能提供探索性证据，不能证明市场普遍有效。
8. 隐私说明与后端任务保留时长存在 30 分钟和 45 分钟的不一致。
9. 原计划中的“多数”“高频”“实质差异”等条件不可复验。

因此当前发布结论是：`NO-GO`。必须先完成 Gate 0。

WP-G0-03 最终复审：PMO `PASS`、反向论证官 `GO`、独立质检官 `PASS`，且 PO
已于 2026-08-18 批准 v0.2。Gate 0 其余工作包仍须独立审查，不代表匿名开放通过。

## 3. 角色与权责

### 产品负责人（PO）

- 身份：用户本人。
- 批准范围、预算、数据规则和测试人群。
- 对每个 Gate 作 `GO / HOLD / STOP` 决定。
- 不代替技术验收，也不需要亲自管理代码细节。

### 总协调与执行负责人

- 身份：当前主 Codex `/root`。
- 接收 PO 授权，拆分一次一个工作包，协调执行代理，汇总证据。
- 可以实施，但不得批准自己的交付。

### PMO

- 固定子代理：`/root/pmo_review`。
- 维护 WBS、状态、依赖、风险、决策和证据索引。
- 只依据可复验证据更新 Gate，不编写产品代码，不代替 QA。

### 反向论证官

- 固定子代理：`/root/red_team_plan`。
- 每个 Gate 都以“为什么不应放行”为立场寻找反例、绕过和证据缺口。
- 输出 `PASS / CONDITIONAL_PASS / FAIL`，不直接修复自己发现的问题。

### 独立质检官

- 固定子代理：`/root/qa_gate_review`。
- 根据冻结规范复测，保存环境、命令、结果和证据。
- 输出 `PASS / CONDITIONAL_PASS / FAIL`，不接受“看起来合理”。

### 工作包执行代理

- 每次只为一个已授权工作包临时创建。
- 只能修改工作包允许的文件，提交实现和测试证据。
- 不能自验、自批 Gate，也不能扩大范围。

上述子代理路径只代表当前 Codex 任务中的固定角色。跨任务续接时，PMO 必须在
推进报告和决策台账中登记新的实际代理身份；替补者不得是被审工作包的执行者。

Gate 放行最低条件：执行证据齐全、质检官 `PASS`、反向论证官没有未关闭
阻断项、PMO 状态完整、PO 明确 `GO`。`CONDITIONAL_PASS` 不得自动进入下一 Gate。

## 4. 状态模型

工作包状态：

```text
BACKLOG → READY → IN_PROGRESS → IN_REVIEW → VERIFIED → CLOSED
                         ↘ REWORK
另有：BLOCKED / CANCELLED
```

Gate 状态：

```text
NOT_OPEN → OPEN → QA_REVIEW → PASS → CLOSED
                         ↘ CONDITIONAL_PASS / FAIL
```

任何时刻只允许一个执行工作包为 `IN_PROGRESS`。

- PMO 在 PO 授权且前置依赖完成后，将工作包从 `BACKLOG` 移入 `READY`。
- 总协调只能启动 `READY` 工作包；执行结束后移入 `IN_REVIEW`。
- QA 或反向论证发现阻断项时进入 `REWORK`，由 PMO 重新排入 `READY`；外部依赖
  无法满足时进入 `BLOCKED`，只有阻断证据关闭后才能恢复。
- Gate 的 `PASS` 表示独立审查条件全部满足；PO 明确 `GO` 后才进入 `CLOSED`。
- `CONDITIONAL_PASS` 或 `FAIL` 必须登记未关闭条件，整改后重新进入 `QA_REVIEW`，
  不能直接转为 `PASS`。

## 5. 严重度

为避免与页面 P1–P9 混淆，缺陷使用 S0/S1/S2：

- `S0`：安全、隐私、重复计费、成本失控、规则偏移、旧入口删除或主链路阻断。一次即暂停。
- `S1`：高频功能、移动输入、按钮、滚动、可读性或错误恢复问题。进入 10 人测试前关闭。
- `S2`：不影响完成率和理解度的轻微视觉或低频体验问题。可记录后排。

真实调用；换算、自动分配、次数、并发和子预算候选见

## 7. Gate 1：匿名开放安全基座

Gate 1 不是“删除登录判断”，而是一次完整的匿名开放安全改造。至少包括：

- 匿名、限次、可失效的体验凭证；不要求账号或 ChatGPT 登录。
- POST、GET、intake 必须校验同一体验凭证；任务与凭证不可逆绑定。猜测、复用、
  过期或撤销的凭证不得读取其他用户结果，日志不得保存原始凭证。
- Direct Reading POST、GET 和 intake 的统一频率、预算和并发控制。
- intake 与 high 调用统一计量；达到硬上限时在模型调用前原子阻断。
- 同一请求同一载荷只调用一次；同一编号不同载荷拒绝且不调用模型。
- 守门数据库、限流或预算服务异常时 fail closed。
- 自动熔断和人工停止开关覆盖 intake 与 reading；GET 是否允许查询已有任务须在规范中冻结。
- 高风险输入在进入正常解卦前按冻结策略阻断或进入安全退路。
- 匿名响应和日志不得暴露问题原文、身份、密钥、提示词或内部异常。
- Git、测试 fixture、issue、提交信息和普通缺陷截图只允许脱敏摘要或合成数据；
  含真实问题的截图必须遮挡。真实反馈、模型原文、联系方式和出生资料不得进入
  仓库，安全测试集必须使用合成问题。
- 保留所有者访问、公开字段白名单、任务状态与不自动重复生成保护。

Gate 1 只验匿名控制面、纵向功能链和跨端联网冒烟，不要求移动端视觉已经完成。
所有付费线上验证必须先由 PO 单独授权；默认使用 fixture/mock。

## 8. Gate 2：移动端可用性

先做一次 P1–P9 全链路巡检，再按 S0/S1 严重性排序，不按页面美术顺序盲目施工。
只允许调整响应式布局、字号、间距、溢出、视口高度、触控区域和必要的错误恢复；
不得改变冻结文案、动线、排盘、解卦 Prompt 或内容契约。

最低设备矩阵：

- iOS Safari：375×667、390×844；
- Android Chrome：360×800、412×915；
- 微信 iOS 和微信 Android 各一台真实设备；
- 竖屏全链路必测，横屏主链路冒烟；
- 覆盖键盘弹出、安全区、返回恢复、滚动恢复、弱网恢复和横向溢出。

必须验证两条冻结路径：

- CLEAR：P1 → P2 → P3 → P6 → P7 → P8 → P9；
- ASK_ONCE：P1 → P2 → P3 → P4 → P5 → P6 → P7 → P8 → P9。

## 9. Gate 3：分级用户测试

### Gate 3A：原 3 人复测

- 三人均独立走完全链路，不接受人工代操作。
- S0 为 0；进入 Gate 3B 前关闭所有 S1。
- 每次体验和模型调用、成本、版本一一对应。

### Gate 3B：固定 10 人首轮测试

- 分母固定为 10 名有效启动者；未完成仍计入分母。
- 至少 8/10 无人工指导独立完成。
- 所有失败均有页面、设备、主原因和证据。
- S0、S1、重复模型调用事故均为 0。
- 结果只作为可用性与价值探索，不宣称市场验证或预测准确性。

### Gate 3C：扩大前质量复核

- 对首轮真实输出进行匿名盲评，检查切题、卦象依据、通用话术、越界和产品声音。
- 使用版本化的“同一现实问题换卦”反事实检查验证判断差异；不得用不同问题换不同卦替代。
- 如果需要真实模型调用，必须单独预算、单独授权和单独保存证据。
- 未通过则回到解卦系统质量主线，不进入最多 30 人测试。

## 10. Gate 4：累计最多 30 人受控公测

30 人口径为从 Gate 3B 起累计最多 30 名不同用户，不是额外新增 30 人。
传播只允许匿名限次凭证、一对一邀请和小范围共研；不公开挂链、不投流、不收费。

最低探索性证据：

- 至少 20 名不同用户完成一次有效体验；
- 至少 15 份结构化即时反馈；
- 至少 8 份单独同意的延迟回访；
- 全部有效启动者完成率不低于 80%；
- S0、安全、隐私、重复计费事故为 0；
- 无开放 S1；
- 实际与预留成本均未超过 PO 冻结的硬上限；
- 联系方式与案例内容分离，无未授权案例传播。

上述数据只支持探索性产品决策，不得外推为普遍市场结论。

## 11. Gate 5：继续、调整或停止

测试开始前，PO 必须在 Gate 0 冻结以下定义及分母：

- “切中最终问题”的评分与通过比例；
- “卦象依据清楚”的评分与通过比例；
- 再次使用意向与实际主动推荐分别报告；本轮不追加第二次付费体验；
- 反事实盲评的样本数、评审方式和通过线；
- 缺失反馈、退出和技术失败如何计入。

只有三种决定：

- `CONTINUE`：技术、安全、成本和质量门均通过，进入下一轮受控扩大。
- `ADJUST`：链路成立但解读价值不足，回到解卦质量主线，不扩大。
- `STOP`：安全、成本、合规边界或核心价值不成立，关闭入口并保留证据。

## 12. QA 否决条件

出现任一项即 `FAIL / NO-GO`：

- 移动 V72 标签，覆盖冻结版本或删除旧版入口；
- 修改 `streamlit_app.py` 或 `iching_tools.py`；这两个迁移前入口在 V73 明确禁止修改；
- 未升级规则版本却改变算法，或让 AI 参与确定性排盘；
- 同一逻辑请求产生超过一次相应模型调用；
- 未预算预留便调用 intake 或 high；
- 限流、预算门或停止开关异常时仍调用上游；
- 总预算或单次成本硬上限被突破；
- 泄露用户敏感资料、出生资料、身份、密钥、提示词或内部诊断；
- 高风险用例产生医疗、法律、证券、赌博、自伤或人身安全方面的越界指令；
- 发布程序未提供的日期、必然保证、第三方读心或虚构事实；
- 任一 S0 未关闭；
- Python pytest、Sites test/build/lint 任一失败；
- 没通过前一 Gate 就扩大真实用户；
- 用“看起来正常”替代可复验证据。
